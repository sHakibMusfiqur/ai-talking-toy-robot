
AI-Powered Talking Toy Robot
Coding Implementation Plan
Part 1: ESP32 Firmware  •  Part 2: Backend / API / Main Web Control Panel + Admin Dashboard
AI chat pipeline (STT/LLM/TTS) is external — integrated only via API calls from the backend.

# Scope Note — The Three Parts
This project has three coding parts. Only Part 1 (ESP32 Firmware) and Part 2 (Backend/API + Main Web Control Panel + Admin Dashboard) are planned and built by you in detail below. Part 3 (the AI Chat Service — STT → LLM → Safety → TTS) is owned and coded separately and is NOT removed from the overall system — it is simply out of scope for your own coding work. Wherever Part 1 or Part 2 needs to talk to Part 3, that connection point is explicitly called out inline (see the highlighted "Connects to Part 3" notes), so the link between all three parts stays visible even though Part 3's internals are not planned here.
# Part 1 — ESP32 Firmware (C/C++, ESP-IDF)
Owner: Software Developer (firmware side), in coordination with the Electronics Engineer. Language: C/C++ on ESP-IDF. No AI logic and no third-party AI provider secrets ever live in this codebase. The firmware never talks to Part 3 directly — it only ever talks to Part 2 (the backend), which in turn calls Part 3.
Phase 1 — Hardware / Software Interface
Lock hardware_config.h: pin map, I2S sample rate/bit depth, PWM channels, servo safe-angle ranges per joint, sensor list, battery-read method. No logic yet — just agreed values with the Electronics Engineer.
Phase 2 — ESP32 Foundation
Boot skeleton: hal/ stub interfaces, state/ machine (BOOT / SETUP / ERROR wired, remaining states stubbed), NVS config storage (encryption-ready even if unused yet), diagnostics/ local log ring buffer, identity/ provisioning check, app/ boot orchestrator.
Test: state-machine transition unit tests; real-board boot test.
Phase 3 — Hardware Control (real drivers)
Replace stubs with real drivers:
hal/mic — I2S audio capture
hal/speaker — I2S/DAC playback
hal/servo — PWM/LEDC, hard-clamped to safe angle ranges, non-bypassable
hal/led — eye/expression indicators
hal/sensors — generic sensor event bus
hal/battery — ADC or fuel-gauge read
Test: bench test each driver in isolation; explicit test that servo clamp rejects out-of-range values.
Phase 4 — Wi-Fi + Network Layer
network/wifi: provisioning flow (local AP or BLE — pick one), stored-credential reconnect, exponential backoff, RSSI reporting. SETUP and CONNECTING states become fully functional. Provisioning here also pairs this one robot to one controller account via a unique per-device pairing code — completing it never grants that controller access to any other robot; each additional robot goes through this exact same one-at-a-time pairing flow independently, on its own hardware, with its own code.
Test: simulate AP loss and verify reconnect timing; reboot-persists-credentials test.
Phase 7 — ESP32 ↔ Backend Communication
network/http + security/: device keypair generation, registration call, challenge-response authentication, JWT storage and refresh. AUTHENTICATING → ONLINE becomes real against the live backend.
Test: real board reaches ONLINE state against staging backend; token-refresh timing test.
Phase 8 — MQTT Communication
network/mqtt: connect using token-derived credentials, publish heartbeat/status/event, subscribe to command and */notify topics, Last Will and Testament, reconnect with re-subscribe logic.
Test: cross-device ACL negative test (device A cannot touch device B's topics); LWT-triggers-offline test.
Phase 12 — Full Voice Pipeline (device side)
voice/wakeword, voice/vad, audio/capture, audio/playback, wired into HTTPS upload/download and the IDLE → LISTENING → PROCESSING → SPEAKING → IDLE state cycle. The backend + AI service return the spoken response — firmware only captures, uploads, and plays it back.
Test: real end-to-end test on hardware; latency measurement; barge-in interruption test.
🔗 Connects to Part 3 (AI Chat Service — external): the audio the firmware uploads is what eventually reaches Part 3 for STT/LLM/TTS — firmware only sees Part 2's HTTPS request/response, never Part 3 itself.
Phase 13 — Emotion + Movement
actions/ module: maps the semantic {emotion, action} values received from the backend into servo/LED sequences, clamped to hardware-safe ranges, with a MOVING overlay that can run concurrently with SPEAKING. Unknown codes fall back to a neutral/idle animation.
Test: each known action code produces the expected sequence; unknown-code fallback test; movement + speech concurrency test (no PWM audio interference).
🔗 Connects to Part 3 (AI Chat Service — external): the {emotion, action} values firmware receives and animates are generated by Part 3 and passed through Part 2 unchanged — firmware just consumes the agreed enum.
Phase 16 — Offline Mode
content/ module: versioned bundle download (canned responses, stories, quizzes), checksum verification, local storage (SPIFFS/LittleFS), and OFFLINE state transitions with local interaction logic.
Test: forced disconnect mid-session test; corrupted-bundle rejection test; offline interaction functional test.
Phase 18 — OTA (Over-the-Air Updates)
ota/ module: check, download, verify (signature + checksum), apply, and roll back firmware using ESP-IDF's dual-partition scheme. Update only ever begins from the IDLE state.
Test: all four required: valid image, tampered image, corrupted download, forced boot failure → automatic rollback.
Cross-cutting firmware rules (apply to every phase above)
TLS certificate validation is never disabled in a production build.
No AI-provider secret or API key is ever embedded in firmware.
Firmware never trusts backend-sent servo angles blindly — hal/servo always clamps to hardware-safe ranges.
No raw child audio is persisted beyond the immediate processing buffer.

# Part 2 — Backend / API + Main Web Control Panel + Admin Dashboard
Stack: Django + Django REST Framework, PostgreSQL, Mosquitto (MQTT), Django Templates + HTML/CSS/JS for the Main Web Control Panel and Admin Dashboard. Owner: Software Developer. The AI chat pipeline (STT → LLM → Safety → TTS) is Part 3 — a separate, externally-owned service — but the backend is the ONLY place in the whole system that talks to it directly. That single integration point (Phase 11 below) is what keeps Part 3 properly connected to the rest of the product.
Phase 5 — Django Foundation
core/ (settings, health check, shared permission classes) and accounts/ (User, Parent, ChildProfile models, signup/login/session). Docker Compose brings up Django + Postgres.
Test: auth tests; ownership-boundary test (a parent cannot see another parent's child).
Phase 6 — Database + Device Management
Full schema migrated up front for every entity — Robot, DeviceCredential, Conversation, Message, AIInteraction, Memory, RobotState, RobotEvent, Configuration, Firmware, OTAUpdate, SafetyEvent, UsageLog, SensorData, AuditLog — even entities other apps only populate later. devices/ app implements registration and pairing endpoints. Pairing is strictly one-to-one and explicit: a controller account only gains access to a robot after that specific robot's own pairing code is entered, and this never cascades to any other robot — owning/controlling one robot grants zero access to any other, even on the same fleet or account; a fleet of many robots means many separate pairing steps, never a shared or bulk access path. Once several robots have each been paired this way to the same account, that account's controller legitimately holds all of them — the restriction is only that pairing must happen per-robot, not that one account is limited to one robot.
Test: migration test; registration/pairing API tests using a simulated device (no real ESP32 required yet).
Phase 7 — Real Device Authentication (backend half)
Challenge/token issuance endpoints exercised by real firmware. Bearer JWT auth on every request; device-scoped queryset enforcement so a device's token only ever authorizes its own device_id.
Phase 8 — MQTT Bridge (backend half)
Mosquitto deployed with ACL configuration; mqtt_bridge/ is a thin translation layer — inbound MQTT messages call the same service functions the REST API would call, and outbound REST/admin actions call mqtt_bridge.publish_command() etc. There is never a second, drifting code path for the same state change. A "command all" or "command several" request from the panel is never a single wildcard publish — mqtt_bridge loops over the selected robot IDs and calls publish_command() once per robot, each publish going only to that one robot's own command topic, so per-device ACL scoping (Section 11-equivalent) is never bypassed even for a bulk action.
Phase 11 — AI Service Integration (the API-calling boundary)
conversations/ app: accepts audio/text plus context, calls the AI service's internal API with the agreed Input Contract, receives the Output Contract (text, emotion, action, safety, audio, memory_writes), persists Message/AIInteraction, applies memory_writes via memory/, logs a SafetyEvent if flagged, and implements the hard-failure fallback (a generic "trouble thinking" response) if the AI service times out or errors.
You own: the HTTP client wrapper, contract validation, persistence, fallback logic, safety-event logging.
You do not own: STT/LLM/TTS/safety-filter internals — that is the separate AI service.
Test: simulated audio-in produces correctly persisted records; forced AI-service-down test triggers the correct fallback without crashing.
🔗 Connects to Part 3 (AI Chat Service — external): this phase IS the live wire to Part 3. The Input/Output Contract shape (Section further below) is the exact interface you call — nothing about Part 3's internal STT/LLM/TTS/safety logic needs to be known beyond this contract.
Phase 12 — Voice Pipeline Endpoint (backend half)
The HTTPS endpoint the robot actually calls: audio upload → proxy to AI service → return TTS audio plus emotion/action to the device, in the same response cycle (or a short-poll follow-up if AI latency requires async handling).
🔗 Connects to Part 3 (AI Chat Service — external): this endpoint is the middle link of the chain Part 1 → Part 2 → Part 3 → Part 2 → Part 1 for every single conversation turn.
Phase 14 — Memory / Context
memory/ app: CRUD plus retrieval logic (simple relevance selection is sufficient for MVP) feeding the AI Input Contract's context field. Parent-ownership-scoped API; dashboard UI for this arrives in Phase 17.
Phase 15 — Educational / Story / Quiz Modes (backend half)
The mode field is plumbed through the existing conversation endpoint (no new pipeline). UsageLog rollups capture minutes active, topics covered, and quiz scores for the dashboard.
Phase 16 — Offline Content (backend half)
content/ app: bundle versioning, a download endpoint, and a checksum included in the metadata response — the device handles the rest.
Phase 17 — Main Web Control Panel + Admin Dashboard
web_control_panel/ (user-facing) and dashboard_admin/ (Django Templates), consuming your own /api/v1/... endpoints so the same backend is mobile-app-ready later. For this prototype, the web frontend is deliberately kept to exactly these two interfaces — one Main Web Control Panel through which the user controls the robot and views its live information, and one separate Admin Dashboard for internal/fleet management — rather than a broader multi-page consumer product. Once this prototype is validated, the same backend/API foundation is extended with a fuller, production-grade UI for commercial release. Visual direction: black/white/soft-gray base with a premium crimson/red accent, glassmorphism where useful, elegant typography, fully responsive — plain CSS design tokens, no heavy JS framework required.
Main Web Control Panel (user-facing): robot pairing; a live info view showing the robot's current status/telemetry (online/offline, battery %, current state, firmware version, Wi-Fi signal), refreshed via polling every 10–15s; direct real-time controls to command the robot (trigger an action/emotion — e.g. wave, greet, go to sleep — plus volume, language default, quiet hours); usage stats, memory management, firmware update trigger, Wi-Fi re-provisioning, and activity/safety history. This single panel is the user's one place to both control the robot and see everything about it. The panel only ever lists and can command robots that have completed pairing for the logged-in account — a robot never becomes visible or controllable here just because the account already controls other robots. When an account has multiple paired robots (e.g. one household with three), the panel lets the user pick exactly one robot and command it on its own, or select several/all of their paired robots at once and send the same command to that whole group in one action — either way, each robot only ever receives commands meant for it. The panel is also not the only, or even the primary, way to operate the robot day-to-day: once pairing/setup is done, normal use is voice-first — the robot listens for its wake word and directly carries out whatever is spoken to it, with no need for the panel to be open. The panel stays available for monitoring, configuration, and occasional manual/remote commands, not as a requirement for ordinary interaction.
Admin pages: user list, fleet/robot management, firmware upload and rollout, logs, system health, safety-event review, analytics, configuration templates.
Test: role-gated access tests (a user cannot reach the Admin Dashboard; user A cannot see user B's data via the Main Web Control Panel).
Note: this prototype intentionally ships only two web surfaces — the Admin Dashboard and the Main Web Control Panel — covering robot control and live information display for the user, nothing more. This scope is what gets built and demonstrated first; once the prototype is validated, it is extended into a fuller, polished production/commercial-grade web product (additional pages, refinement, possibly a native app per the future-expansion roadmap) for actual sale.
Phase 17 (continued) — UI/UX Design Specification: Main Web Control Panel
This section is the binding visual and interaction spec for the Main Web Control Panel (and, with denser layouts, the Admin Dashboard). It is written so the coding agent does not have to invent colors, fonts, screens or behaviors. Goal: a luxury, cinematic, modern-robotics look that is still fast, obvious and friendly for a normal parent — functionality first, decoration second. Implementation stays Django Templates + one CSS tokens file + small vanilla JS; no frontend build pipeline.
1. Design principles
Clear before clever: the user must see "which robot, is it online, what can I do right now" within 2 seconds of opening the panel.
Dark-luxury by default, light theme available: black/graphite base, soft-white text, one crimson accent used sparingly so it always means "primary action" or "brand".
One accent rule: crimson is never used for status. Status (online, warning, error) has its own colors plus an icon and a word, so nothing depends on color alone.
Glass only where it adds depth: hero cards, modals, sidebar. Data tables and forms stay solid for readability and speed.
Safe by design: risky actions (group commands, sleep-all, factory reset, delete memory) always ask for confirmation and show exactly which robots are affected.
Mobile-first responsive: most parents will open this on a phone. Every screen must be fully usable at 360px width.
2. Color system (define as CSS custom properties on :root in tokens.css)
Dark theme (default):

Light theme (toggle in header; also follows prefers-color-scheme on first visit; user choice is remembered):

Signature effects: (a) primary buttons use a subtle gradient from --accent to --accent-deep with a faint crimson glow (box-shadow 0 0 24px rgba(208,25,58,0.25)); (b) hero robot card has a soft radial crimson light behind the robot illustration at about 12% opacity; (c) online status dot has a slow pulse. All text/background pairs must pass WCAG AA (4.5:1 body, 3:1 large text).
3. Typography
UI font: Inter (Google Fonts, weights 400/500/600) for all body, labels, buttons and tables.
Display font: Playfair Display or Cormorant Garamond (600) only for large page titles, robot name and big numbers, to give the elegant premium feel. Never for small text.
Bangla: Hind Siliguri (or Noto Sans Bengali) with the same weights; the panel must render Bangla and English correctly and let the user switch interface language.
Fallback stack: system-ui, -apple-system, Segoe UI, Roboto, sans-serif — every web font must have a real fallback.
Scale: 12 / 14 / 16 (base) / 20 / 24 / 32 / 44 px; line-height 1.5 for body, 1.2 for headings; minimum tap target 44x44 px.
4. Layout and navigation
Desktop (1024px and up): fixed left sidebar (glass, 240px, collapsible to icons) + top bar + content area with 12-column grid, max width 1280px.
Tablet: sidebar collapses to an icon rail.
Mobile: sidebar becomes a bottom tab bar with 5 items (Home, Control, Chats, Insights, Settings); robot switcher stays in the top bar.
Top bar (always visible): robot switcher dropdown (shows nickname + status dot), notifications bell, language toggle (EN / বাংলা), light/dark toggle, profile menu.
Global banners: a slim banner under the top bar for "Robot offline — last seen 12 min ago", "Firmware update available", "Low battery 15%". Only one banner shown at a time, most severe first.
5. Screens and what each must contain
Sign in / Sign up: centered glass card on dark background with a faint animated crimson gradient; email + password, show/hide password, "forgot password", clear inline errors. Optional MFA later.
Onboarding / Add robot wizard: 3 steps with a progress bar: (1) power on the robot and note the pairing code, (2) enter the code and give it a nickname (e.g. "Ayaan's Robo"), (3) choose child profile, language and Wi-Fi help. Success screen with a small robot wave animation. Wizard can be repeated for each new robot.
My Robots (home): grid of robot cards, one per paired robot: illustration, nickname, status chip (Online / Sleeping / Offline / Updating), battery bar, current state, last seen, and buttons "Open" and "Quick command". A "+ Add robot" card at the end. Checkbox on each card enters group-select mode.
Robot Control (main screen): hero card with robot name, big status, battery ring, Wi-Fi bars, firmware version. Below it a Quick Actions grid of large buttons: Wave, Greet, Dance, Sleep, Wake, Say Goodnight, Tell a Story, Start Quiz. Beside it a volume slider, language selector, and "Quiet hours" toggle. A "Speak this" text box lets the user type something for the robot to say (goes through the normal safety pipeline). Every command shows an instant toast: Sending, Delivered, or Failed with a retry button.
Group control mode: when 2+ robots are selected, a sticky bottom action bar appears: "3 robots selected" + the same quick actions + Select all / Clear. Sending opens a confirmation sheet listing each robot by name; after sending, a per-robot result list (delivered / failed / offline) is shown so nothing fails silently.
Live Info / Telemetry: online/offline, battery %, charging state, current state-machine state (Idle, Listening, Speaking...), Wi-Fi signal, firmware version, last heartbeat, uptime. Auto-refresh every 10-15 seconds with a small "updated 5s ago" label; simple inline-SVG sparkline for battery over the last 24h.
Conversations: chat-style history (child bubbles left, robot bubbles right) with date filters and search, language badge, and emotion icon per robot reply. Flagged/safety items shown with a subtle shield icon (details expandable). Delete conversation button respecting retention rules.
Memory: list of things the robot remembers about the child (favorite animal, etc.) as removable chips/cards with "Forget this" and "Forget everything" (confirmation required).
Insights (learning and usage): daily active minutes, topics covered, quiz scores and streaks as simple bar/line charts and progress rings; weekly summary card. Friendly wording, no jargon.
Settings per robot: name, child profile, default language (Bangla / English / auto), volume limits, quiet hours schedule (day-by-day time pickers), allowed modes (free chat, stories, quiz), content strictness level, Wi-Fi re-setup, firmware update (schedule window), "Restart robot", "Unpair robot" and "Factory reset" in a red danger zone with double confirmation.
Notifications center: safety alerts, low battery, robot offline, update finished. Each item has severity color + icon, timestamp, and a link to the relevant screen.
Account: profile, password change, child profiles (first name + age band only), data and privacy page (what is stored, retention period, export/delete my data).
6. Reusable components (build once in base templates)
Buttons: Primary (crimson gradient), Secondary (outline), Ghost, Danger (outlined red until confirmed). Loading state with spinner, disabled state clearly dimmed.
Status chip: colored dot + text (Online, Offline, Sleeping, Updating, Low battery).
Cards: glass card and solid card variants, 16-20px radius, 1px border, consistent 16/24px padding.
Form controls: toggles, sliders with live value, segmented controls (language), time pickers, inline validation messages.
Feedback: toasts (bottom-center on mobile), confirmation modal / bottom sheet, skeleton loaders while data loads, friendly empty states with an illustration and one clear action, error states with a retry button.
Data display: battery ring, Wi-Fi bars, sparkline, progress bar, timeline list.
7. Glass, motion and depth
Glass recipe: background rgba(255,255,255,0.04), backdrop-filter blur(18px) saturate(120%), border 1px rgba(255,255,255,0.08), radius 20px, plus a soft top-edge highlight. Provide a solid --surface fallback when backdrop-filter is unsupported.
Motion: 150-250 ms ease-out for hovers, sheet and modal transitions; gentle fade-up on page load; pulse on the online dot; a short success tick animation after a command is delivered. Respect prefers-reduced-motion by disabling non-essential animation.
Performance budget: no heavy animation libraries; icons as inline SVG (Lucide-style, self-hosted); total CSS under about 60 KB; pages usable on a mid-range phone over 4G.
8. Real-life and professional features the panel must cover
Emergency controls: always-visible "Stop / Sleep now" button on the Control screen that immediately quiets and rests the robot.
Trust and safety visibility: parent can see safety alerts, set content strictness, and read what data is stored; clear privacy wording suitable for a children's product.
Connection awareness: honest states — "Offline, commands will not be delivered", last-seen time, reconnect hints (check Wi-Fi, power). Commands to an offline robot are not queued silently; the user is told.
Multi-robot clarity: robot nickname and color tag appear on every screen so the user never sends a command to the wrong robot.
Multi-user readiness: layout and roles allow a second guardian to be invited later (view-only or full control) without redesign.
Accessibility: keyboard navigable, visible focus ring in accent color, labels on all controls, alt text, AA contrast, support for browser text zoom to 200%.
Localization: all UI strings in translation files (English and Bangla) from day one; dates, numbers and time zone shown in the user's locale (Asia/Dhaka by default).
Installable feel: optional PWA manifest so the panel can be added to the phone home screen with the app icon and a dark splash screen (no offline caching of private data).
Support and help: help icon with short "how to pair", "robot offline?" and "update" guides; a contact-support link; app version shown in Settings.
Session security: auto sign-out after inactivity, "sign out of all devices", visible last-login info.
9. Admin Dashboard styling
Uses the same tokens, fonts and components but with denser layouts: data tables with sticky headers, search and filters, status chips, pagination, bulk actions, log viewer with severity colors, and firmware rollout progress bars. Table header uses --accent-deep. Admin screens are clearly marked (small "ADMIN" badge in the top bar) so staff never confuse them with the user panel.
10. Prototype must-haves vs later
Prototype must-have: login, add-robot wizard, My Robots grid, Robot Control with quick actions, group control with confirmation and per-robot results, live info, settings (volume, language, quiet hours), notifications banner, dark theme, EN/Bangla toggle, responsive layout.
Add for production: Insights charts, light theme polish, multi-guardian invites, PWA install, data export, richer animations, illustrated empty states, analytics-driven tweaks, native mobile app.
Acceptance test: a new parent on a phone can sign up, pair a robot, send "Wave", see it delivered, and find the robot's battery and online status in under 3 minutes without help; the same flow works in Bangla; all screens pass an automated contrast and keyboard-navigation check.
Phase 18 — OTA Management (backend half)
firmware/ app: upload, versioning, and rollout endpoints, plus signing metadata storage. Actual firmware signing happens only in CI, never on a developer laptop.
Phase 19 — Security Hardening
Rate limiting via DRF throttle classes (especially on conversation and auth endpoints), an admin-triggered credential-rotation action, and a dedicated pass of auth-bypass, replay, and injection testing.
Test: auth bypass, token replay/expiry, MQTT ACL bypass, and API injection attempts — all must be correctly rejected.
Phase 20 — Observability
Per-service /health endpoints, metrics (request latency, error rate, AI-call timing, MQTT connection counts), a log-redaction audit confirming no raw child data appears at default log level, and alerting on failure conditions.
Phase 21 — Full System Testing
Every user flow executed against a staging environment: voice pipeline, offline fallback, OTA, dashboard, failure-matrix fault injection, and a fresh pass of the safety adversarial test set.
Phase 22 — Production Deployment
Production Docker Compose stack (nginx TLS termination, Django, Postgres, Mosquitto, Redis/Celery if adopted), automated backups with a tested restore drill, and the first real device registered in production.

## Decision Records (appended 2026-09-29 — original document above preserved unchanged)

### 2026-09-29 — PostgreSQL → MongoDB (authorized)

- **Decision:** The Phase 5 database is **MongoDB 7.0** (`django-mongodb-backend` 5.2.4) instead of PostgreSQL, for Phase 5 and until a later authorized decision record supersedes this one. Owner-approved before implementation.
- **Scope of change:** All historical references above to "PostgreSQL" (Part 2 stack line, Phase 22 production stack) remain as written — they are the original plan and are superseded by this record for database selection only. Mosquitto/MQTT, Django, DRF, Django Templates, and every API contract, ownership rule, pairing rule, and test requirement in this document are unchanged.
- **Consequences:** `docker compose` brings up Django + MongoDB single-node replica set (`rs0`); primary keys are ObjectIds serialized as JSON strings (never integers); no integer counters; signup transactionality uses `django_mongodb_backend.transaction.atomic()`; migrations for `auth`/`contenttypes` are generated into `backend/mongo_migrations/`; tests run against a real MongoDB test database.
